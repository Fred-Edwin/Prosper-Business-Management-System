## 1. What this task is

Milestone 1's screens were originally designed in an earlier session, but drifted from a consistent design system: inconsistent shells, hardcoded colors/spacing instead of tokens, duplicated/diverging components (e.g. two different friction-delete dialogs), and several off-token dark UI patterns. A full audit was done, followed by a from-scratch rebuild of a single canonical Component Kit (shells, buttons, forms, chips, tables, tabs, drawers/dialogs, stat tiles, banners, bulk-entry grid, utility components, bottom sheet). That kit is **approved and final — do not redesign any kit component**. This task is now the last step: **reassemble every real screen using only the approved kit**, preserving each screen's real data/content but rebuilding its structure and styling from scratch.

Read `docs/design/design-principles.md` in full before touching anything — it documents the binding house rules (square-corner tables, no avatars in attribution columns, tabular-nums, etc.) referenced throughout the kit.

## 2. Non-negotiable process (do not deviate)

For every screen on the list below:

1. **Screenshot + inspect the OLD artboard** (`get_tree_summary` + `get_screenshot`). This step is for **content and requirements extraction only** — read off the real data (names, prices, categories, dates, quantities, copy) so nothing gets lost. Do NOT copy its layout, spacing, or colors — those are exactly what's being replaced.
2. **Duplicate the approved Admin Shell** (`Admin Shell — Desktop (Full-Height Sidebar)`, id `649-0`) as the starting point for every desktop screen, or the approved Mobile Shell (`Mobile Shell — Sidebar Drawer Open (Admin & Staff)` id `1ZP-0`, `Mobile Shell — Admin (Drawer Closed)` id `6B1-0`, or `Mobile Shell — Staff (Drawer Closed)` id `4Y-0`) for mobile screens. Never duplicate an old screen.
3. **Set the correct active nav state** (deactivate whatever was active by default, activate the item matching this screen) reusing the exact icon/indicator-bar pattern already in the shell.
4. **Rebuild the content** using ONLY pieces from the Component Kit artboards (list in §3) — via `<x-paper-clone node-id="...">` in `write_html`, or by hand-writing HTML that uses the exact same `var(--token)` values the kit components use. Never introduce a new hardcoded hex/px value. If a screen needs something with no kit equivalent, STOP and flag it — do not invent a one-off. (In practice everything needed should already exist; the kit was built specifically to cover every real screen's needs per a full coverage audit.)
5. **Content-frame spacing standard** (binding, set by the Admin directly in Paper): every desktop screen's Content frame uses **`gap: var(--sp-8)` (24px) between sections** and **`paddingInline: var(--sp-6)` (16px)** horizontal padding. Reference: node `6ZS-0` on artboard `6ZO-0`. Apply this consistently to every desktop screen's content area.
6. **Type in the real data** extracted in step 1 — every product name, price, date, quantity must match the old screen's actual values, not placeholder/lorem content.
7. **Screenshot to verify** — check nothing was dropped, alignment/tokens are correct, no clipped text (watch for `white-space: nowrap` + `flexShrink: 0` on short fixed-width labels like "KES", "kg" — this bit us twice already).
8. **Position the finished artboard** in the row that starts with Login — Desktop (`15K-0`, at `top: 4407px, left: 0px`) and Login — Mobile (`16J-0`, `left: 1850px`). Continue left-to-right along `y: 4407px` with an 80px gap between artboards. **Important gotcha we hit:** when duplicating something that lives inside a Component Kit artboard (e.g. cloning the Drawers & Dialogs kit's Edit Drawer as a base), the duplicate stays nested as a child of that kit artboard — `update_styles` on `top`/`left` silently repositions it within its parent instead of moving it on canvas. You MUST call `move_nodes` with `parentId: 'root'` (root is `root_node_1-0`) to lift it to top-level artboard status BEFORE setting `top`/`left`. Verify with `get_node_info` that `parentId` is `root_node_1-0` before trusting a position.
8a. **Every drawer/dialog screen (any screen whose panel uses `--surface-panel-tint`) MUST be wrapped in its own opaque white backing artboard — never make the panel itself the top-level artboard.** `--surface-panel-tint` is only ~22% opaque; it's designed to sit over a white page (exactly like the Login sign-in card it was extracted from). If the panel frame IS the artboard, Paper's dark canvas shows through and the panel renders as a muddy dark blob instead of a soft lavender veil — this happened to both Product Drawer and Product Delete Dialog and had to be fixed after the fact. Do it right the first time:
   - `create_artboard` with `backgroundColor: "#FFFFFF"` (or `var(--surface-page)`), sized generously around the panel (e.g. 900×960 for a drawer, 900×600 for a dialog).
   - For a **drawer**: `display: flex; alignItems: flex-start; justifyContent: flex-end; padding: 40px` (docks the panel to the right edge like a real slide-over).
   - For a **dialog**: `display: flex; alignItems: center; justifyContent: center` (centers the panel like a real modal).
   - `move_nodes` the panel frame into this new artboard as a child, then rename the panel (e.g. "Drawer Panel" / "Dialog Panel") since the artboard now owns the screen's real name.
   - Position the new backing artboard in the login row per the rule above — not the inner panel.
   - Reference examples already fixed this way: `796-0` (Product Drawer backing artboard, panel inside is `75N-0`) and `797-0` (Product Delete Dialog backing artboard, panel inside is `78E-0`).
9. **Do NOT delete the old artboard.** All old screens stay in the file, untouched, until the Admin explicitly approves bulk-deleting them at the very end of this whole effort. Never delete anything unless told to.
10. **Update the checklist below** (or repost it) after each screen so progress stays visible.

Key facts about the kit, learned the hard way — do not relitigate these:

- **Colors are OKLCH tokens**, not hex. All `--color-*` tokens were converted from hex to OKLCH (same visual values) so they can be tuned along single dimensions (L/C/H) later. Never add a raw hex color — always reference or extend a token.
- **`--surface-panel-tint`** (`#A690B838`, a muted lavender veil) is the approved background for floating overlay panels — the Friction Delete Dialog and the Edit Drawer already use it. It originated from the approved Login sign-in card's background and must NOT be applied to primary page content (that stays `--surface-page`, pure white) — only to floating drawers/dialogs.
- **Chips/status indicators are dot + colored text only — no filled pill background.** This was an explicit Admin correction; do not reintroduce filled chip backgrounds.
- **No "CORRECTED" chip exists** — it was deliberately removed pending a future, more subtle design decision for showing corrected ledger figures. Do not re-add a chip for this; leave corrected values as plain colored text for now (see the Dense Ledger's "Issues (-)" cell pattern in the Tables kit) unless told otherwise.
- **Tables are fluid-width** (`width: 100%`, one text column set to `flex-grow: 1`, everything else fixed-width) with a fixed `gap` (never make gap itself stretch). **Alignment rule:** numeric/money columns right-aligned, everything else (including the trailing "Edit" column/action) left-aligned. Every table row has a trailing **Edit** column/link — this is the one standardized way to open the row's edit drawer; do not use `⋮` menus or other ad hoc edit affordances.
- **Table header style:** subtle blue tint background (`--color-info-bg`) with `--color-info` label text, and a **`--color-gray-600` bottom border** (not `--border-subtle` — this was a specific Admin correction, stronger than the default hairline).
- **Stat tiles for dashboards are a hairline-divided strip**, NOT separate bordered/boxed cards. One continuous container, sections divided only by a 1px vertical hairline (`--border-subtle`) with padding on either side — no per-stat border or background. This was an explicit Admin design correction (previous boxed-card version was rejected). The separate **Dense Summary Strip** pattern (dark `--color-gray-900` background, used for sticky footers / mobile banners) is a different, valid pattern — don't confuse the two.
- **Friction-gated delete dialog**: ONE canonical version (based on the old Asset Delete Dialog's structure — icon badge + "PERMANENT IRREVERSIBLE ACTION" subtitle), with two states already built (disabled/pending-retype and enabled/confirmed-red). Reuse via clone; retitle "Delete Record" → "Delete {Entity}" and update the body copy per entity type, exactly as done for Product Delete Dialog.
- **Segmented controls** need the shadow-lift + accent-text active-state treatment (see Form Controls kit) — a flat white pill with no shadow reads as "not selected."
- **Small fixed-width labels clip easily** — always add `flexShrink: 0` and `whiteSpace: nowrap` to short unit/currency labels (e.g. "KES", "kg") sitting next to a flexible sibling, or they wrap to two lines.
- **Bottom Nav (Staff mobile shell)** — the approved Mobile Shell — Staff base (`4Y-0`) originally shipped with only a hamburger-drawer header + a screen-specific sticky action bar, no persistent bottom tab bar. Every Hub/Stock Levels screen in this sprint needed one (Hub/Stock/History), built ad hoc the first time on the Store Manager Hub. **Now added directly to the canonical shell component itself** (`4Y-0`, as a 5th child after the Sticky Action Bar) so every future duplicate of the shell already includes it, and also documented as a standalone sample in the Utility & Layout kit (`6WD-0`) for quick reference. Both the Sticky Action Bar (screen-specific primary action, e.g. Save order / Confirm Kitchen Issue) and the Bottom Nav (persistent Hub/Stock/History) now coexist in the shell's anatomy — not every screen uses both; use whichever fits the screen's need. This is not a duplicate of the desktop Admin sidebar; it's the primary persistent nav for the staff shell's frequent destinations, with the drawer reserved for secondary/rare items, same as any standard mobile app split between bottom tabs and a hamburger menu.

## 5. Design decisions already made — do not re-litigate

These were explicitly decided by the Admin in conversation. Follow them; don't ask again unless something is genuinely ambiguous within them.

1. **No standalone `/admin/stock/reconciliation` screen.** The Admin explicitly rejected this as a separate page. Instead, add a **Reconciliation section** to the Admin Financials screen — a way to surface outstanding payments awaiting receipt, and receipts without a matching payment, using the existing Stock Purchases table's "Delivery Status" column as the data source. Design this as a filtered view or dedicated section within Financials, not a new route.
2. **No standalone `/store-manager/receipts` or `/canteen/receipts` screens.** Purchase deliveries and stock transfers both become **persistent banners** on the respective mobile hub (Store Manager Hub, Canteen Hub) that stay pinned until the user Accepts/Matches or Flags a discrepancy — modeled on the existing incoming-transfer banner pattern. Once resolved, the action becomes a line in the hub's "Today's ... Log" timeline. Both banner types (transfer-received vs. purchase-delivery-pending) get this same persistent treatment — this was an explicit either/or the Admin resolved in favor of "both are banners," not "transfers only."
3. **Financials is in-scope for Milestone 1** despite not being named in `docs/milestones/milestone-01-the-business-exists.md` §3's screen table — the Admin confirmed it should be rebuilt now, not deferred.
4. **Store Manager and Canteen both get Stock Levels screens** (`/store-manager/stock`, `/canteen/stock`) — these were missing entirely and the Admin asked for them to be designed fresh as part of this pass, not deferred.
5. **Canteen gets its own Transfer Dispatch screen**, mirroring Store Manager's — the Admin confirmed Canteen is not purely a transfer-destination role.
6. **Ledger Maximize button = the general Icon Rail sidebar-collapse state, not a separate one-off shell variant.** The old screen had a dedicated "Admin Shell — Ledger Maximized" artboard built just for this one screen. The Component Kit rebuild separately produced a general-purpose "Sidebar Collapsed, Icon Rail" state (`67T-0`) usable on any screen. Confirmed: retire the old screen-specific variant: the Ledger's Maximize button should trigger the same general Icon Rail collapse every other screen would use, not a bespoke behavior. Rationale: a screen-specific shell variant is exactly the kind of divergence this reassembly sprint exists to eliminate, and the general state already reclaims the same width for no extra build cost. See §8 for the follow-up action this implies.
